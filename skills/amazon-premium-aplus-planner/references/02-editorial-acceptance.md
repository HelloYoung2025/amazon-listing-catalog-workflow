# 02 · 编辑验收与交付

验收看的是**买家能不能用这套 A+ 做对决定**，不是模块数量。

## 四项检查（对胜出序列做一次）

| 检查 | 问法 | 通过标准 |
|---|---|---|
| 理解 | 只看首屏模块 5 秒，这是什么、给谁、解决什么？ | 三个模拟买家答案一致且与意图简报一致 |
| 选对 | 一个 36D / 两个孩子 / 想买 2 件装的买家，能从 A+ 里找到该买哪个吗？ | 不需要回到五点或问客服 |
| 拒错 | "不该买的人"读到第几个模块知道不适合？ | 在第 3 个模块之前，且是被尊重地告知（条件句），不是被吓走 |
| 手机端 | 390px 宽下首屏能看见什么？图上文字读得清吗？ | 关键事实在原生文字里；图上文字 ≤ 12 词且不被裁掉 |

任一项不过 → 回到模块序列改，不加模块。

## 独立 QA 提问（重建时给一个没看过答案的评审）

给它 Skill、任务请求、最少的原始证据，不给预期答案。让它检查：
- 是否先调查可观察来源再提问
- 问题是否分批、实质、不重复
- 是否有本品主张只靠老板记忆 / 竞品 / 评论 / 推断
- 模块数量与顺序是选出来的还是模板继承的
- 所有适用 child 是否都有表达
- 错误用户与高风险限制是否在购买前可见
- ALT、AI 素材、手机构图、原生文字是否尊重证据
- 结论与写入权限是否正确划界

## 交付内容

Embedded：写进主入口 HTML 第 8 节"A+ 交接简报"下：模块序列总览（一行一模块：动作 / 决策问题 / 标题）→ 每模块标准卡（可展开）→ 视觉简报与素材记录 → ALT 清单 → 能力核查表（模块 / 是否可用 / 核对日期 / 来源）→ 证据请求清单（模块 / 句 / 需要什么 / 降级句）→ Brand Story（如适用）。

Standalone：单独 HTML，用 `assets/full-width-report-shell.html`，另加预研合成、第一轮回答记录、取舍表、买家评审摘要。

## HTML 要求

自包含、无网络依赖（有意引用的外链除外）；100% 浏览器宽度、少量边距；不是 A4 / 分页 / PDF 卡片；语义标题与表格表头；表格与图库可滚动或展开；关键事实与结论是原生文字；截图有 ALT；不声称有未实现的 tab / 持久化 / 复制按钮；桌面、平板、手机检查用任务合适的宽度（390px 是实用的手机检查，不是平台规则）；写明输出日期、来源日期、当前/阻塞状态、负责人、签核。无表单、无提交、无可编辑事实、无线上账号控件。

## 版本与回滚（工作稿层面）

每次交付记：版本号、日期、基于哪一版 Listing 定稿、改了哪些模块、为什么。旧版文件保留不覆盖。正式 Baseline / Change Set / 回滚记录在 publish-gate 的 Bundle 里。
